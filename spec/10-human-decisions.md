# 10 · 人工决定与升级协议

## 1. 定位

本篇规定 Agent 何时必须把决定交给人、如何记录、等待期间如何继续工作。
它只定义通用升级机制；哪些具体事项需要人拍板，由所属业务库、项目 `AGENTS.md` 或合同纪律另行定义。

## 2. 默认边界

本地、可逆、已有明确授权且有验证手段的工作，Agent 可以按流程执行。
出现以下任一情况时，【必须】升级，不得自行补全授权：

- 难以撤销或影响范围超出当前工作区的动作；
- 对外发布、共享分支合并、生产环境或真实外部账号的变更；
- 生产数据删除、迁移、权限修改或敏感信息处理；
- 业务库或项目规则明确列为人工决定的事项；
- 没有可验证完成标准，继续执行只能靠猜的情况。

【必须】Agent 可以准备选项、证据、影响分析和建议，但不能代替被授权人作出决定。

## 3. `BLOCKED` 记录

遇到需要人工决定的事项，在工作项或台账中写：

```text
BLOCKED: <需要人决定的一句话>
```

并在 `产出/decisions/` 建立决定单，至少包含：

| 字段 | 内容 |
|---|---|
| 问题 | 需要决定什么，不把多个问题揉在一起 |
| 阻塞原因 | 为什么 Agent 无权或无法可靠决定 |
| 选项与代价 | 可行选项、各自影响和可逆性 |
| 建议 | Agent 的建议及理由，可写“无建议” |
| 证据 | 相关文件、命令结果、差异或风险位置 |
| 决定人 | 有权拍板的人或角色 |
| 请求时间 | 何时提交给人决定 |
| 决定与日期 | 决定内容、决定人和实际决定日期 |
| 恢复条件 | 哪个结果允许哪些工作继续 |

【必须】不能先执行再补决定单；没有决定时，相关部分保持未执行。
【应当】决定单保持一个问题一份记录，后续引用同一编号，不在多处复制不同版本。

## 4. 等待期间的工作纪律

1. 只暂停依赖该决定的部分，继续做不依赖它的工作。
2. 不通过删除测试、降低门禁、换路径或缩小交付物来绕过阻塞。
3. 不把“用户没有回复”解释成默认同意；只有明确约定的默认规则才能生效。
4. 同一阻塞重复出现时，复用原决定单追加信息，不制造多份相互矛盾的请求。
5. 决定作出后，先核对决定内容与实际执行范围，再恢复工作并更新台账。

## 5. 台账与审计

台账的“遗留问题”保留活跃 `BLOCKED` 摘要；决定作出后，在“决策记录”写明决定、决定人、日期和决定单路径。
【必须】恢复工作的证据必须能追溯到决定单与后续验证，不能只写“已沟通”。

## 6. 反模式

- ❌ 把所有小问题都交给人，形成不必要的注意力负担。
- ❌ 把高风险动作包装成“临时试一下”，规避人工授权。
- ❌ 遇到阻塞就停掉整个工作区，不做任何可独立推进的事项。
- ❌ 口头拍板后无记录，下一次会话重新争论同一问题。
- ❌ 将 Agent 生成的建议当作人的正式决定。
