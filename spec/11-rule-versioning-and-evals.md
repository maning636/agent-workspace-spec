# 11 · 规则版本锁定与组合验证

## 1. 定位

规则库本身也是会变化的输入。项目必须知道自己使用了哪些规则版本，以及这些版本是否经过同一组场景验证。
本篇只规定版本记录和验证纪律，不要求不同规则库共用版本号或同步发版。

## 2. 独立版本，兼容组合

1. 每个规则库独立使用语义化版本；内部功能变化按自己的节奏发布。
2. 【必须】项目锁定具体 tag、commit 或不可变发布包，禁止用 `main` 代表一个可复现组合。
3. 交接信封、需求包等业务 schema 单独标版本；规则库版本号不能代替 schema 版本号。
4. 只有破坏兼容的变化才需要相关库协调：删除或改名字段、改变编号含义、改变交接状态、改变证据格式或人工授权边界。
5. 普通文档修订和向后兼容的新增，不应迫使其他库同步发布。

## 3. `rules.lock.yaml`

【必须】需要组合多个规则库的项目，在工作区根目录维护 `rules.lock.yaml`，模板见 `templates/workspace/rules.lock.yaml`。
至少记录：

| 字段 | 含义 |
|---|---|
| `opc_playbook` | 经营规则库的已验证版本 |
| `engineering_standard` | 工程规则库的已验证版本 |
| `agent_workspace_spec` | 工作区规范的已验证版本 |
| `handoff_schema` | 通用交接信封版本 |
| `requirement_schema` | 需求包与编号映射版本 |

【必须】实际使用时把模板占位值替换为真实、不可变版本，并记录组合验证所使用的样例和日期。
没有使用某个库时可以省略对应字段，但不得保留看似真实版本的占位值。

## 4. 组合验证

组合验证回答“这些版本能否配合”，不回答“真实客户项目是否成功”。

【应当】至少保留以下虚构场景，并在相关契约变化后重跑：

1. **正常交接**：合格输入被下游接受并锁定基线。
2. **拒绝交接**：缺必填字段、哈希不符或业务门禁不满足时被退回。
3. **变更重开**：基线变化产生新版本，旧版本保留并可追溯。
4. **边界场景**：探索任务携带明确假设时，不被不适用的完整交付门禁拦截。
5. **回滚场景**：组合升级失败后能恢复上一组锁定版本。

【必须】验证记录写明各库版本、schema 版本、执行命令、实际输出和验证日期；禁止只写“已测试”。
【应当】优先复用各库已有测试与虚构样例，不为形式统一另建一套重复框架。

## 5. 升级与回滚

```text
发现变更 → 判断是否为破坏性契约变化 → 更新相关库版本
→ 重跑组合场景 → 更新 rules.lock → 项目主动采用
```

- 规则库升级不自动改变进行中的项目；项目主动更新锁文件后才采用。
- 采用失败时恢复上一份 `rules.lock.yaml`，并记录失败原因。
- 旧交接件继续引用其原始 schema；需要迁移时单独产出迁移版本，不原地改写历史。

## 6. 总览与许可证边界

- `产出/OVERVIEW.md` 是从各权威状态生成的只读投影，禁止手工维护另一份状态。
- 组合使用不合并各库许可证；发布包必须保留各自 LICENSE、NOTICE 和来源信息。
- 真实客户材料、密钥和生产日志只留在受控项目，不进入公开验证场景。

## 7. 反模式

- ❌ 三个库都改成同一个版本号，却没有跑过一次组合场景。
- ❌ 项目默默跟随 `main`，规则变化后无法复现上次行为。
- ❌ 用同一份手工 OVERVIEW 掩盖各库状态已经分叉。
- ❌ 把虚构样例通过写成真实客户验收通过。
