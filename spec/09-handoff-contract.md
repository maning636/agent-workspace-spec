# 09 · 通用交接契约

## 1. 定位

本篇定义工作区内不同角色、技能或规则库之间交接产物的**通用信封与接受过程**。
它是 L5 的协作协议，不是业务状态机，也不规定某类项目必须经过哪些阶段。

【必须】业务产物的字段、门禁和完成定义由所属业务库或技能定义。本篇只回答：
产物是谁交的、交给谁、哪个版本、现在是否被接受、权威原件在哪里。

## 2. 基本原则

1. **原件唯一**：交接产物只有一个权威 `source`，其他位置保存引用，不维护可写副本。
2. **版本明确**：提交后的内容变化必须产生新的 `artifact_version`，不能原地覆盖旧版本。
3. **接受才算交接**：上游写完不等于下游接受；下游须检查输入是否满足自己的开工条件。
4. **门禁按场景生效**：只有所属流程明确声明的硬门才能因缺字段阻断开工；探索性工作可以携带已标记的假设。
5. **数据最小化**：信封只放元信息与引用，不复制客户原文、凭据、合同、日志或其他敏感内容。

## 3. `handoff/v1` 通用信封

【必须】每个交接产物附带以下字段；可以放在产物头部的 YAML、同名 sidecar 文件或交接单中。

| 字段 | 类型 | 含义与约束 |
|---|---|---|
| `schema_version` | 字符串 | 固定为 `handoff/v1`；信封结构变化时升级 |
| `artifact_version` | 字符串 | 本次产物的唯一版本，发出后不复用 |
| `business_id` | 字符串 | 所属业务或工作项标识；无业务 ID 的探索任务使用工作区本地 ID |
| `producer` | 字符串 | 产出方角色、技能或规则库，不使用含混的“AI” |
| `consumer` | 字符串 | 预期接收方角色、技能或规则库 |
| `status` | 枚举 | `draft` / `submitted` / `accepted` / `baselined` / `superseded` |
| `source` | 路径 | 权威原件的相对路径或受控 URI，不得指向聊天记忆 |
| `hash` | 字符串 | 权威原件的内容摘要，建议 `sha256:<hex>` |
| `created_at` | 字符串 | 本版本创建时间，使用带时区的 ISO 8601 |

示例：

```yaml
schema_version: handoff/v1
artifact_version: H-0001-v1
business_id: LOCAL-0001
producer: workspace-skill
consumer: workspace-reviewer
status: submitted
source: 产出/handoffs/H-0001.yaml
hash: sha256:<由脚本计算>
created_at: 2026-11-02T23:59:00+08:00
```

## 4. 生命周期

```text
draft → submitted → accepted → baselined → superseded
           │             │
           └── 退回 draft ┘
```

| 状态 | 含义 | 允许动作 |
|---|---|---|
| `draft` | 产出方仍在整理，缺项和假设可以存在 | 修改内容，不交给下游当正式输入 |
| `submitted` | 产出方认为已满足提交条件 | 下游检查；可接受或写明原因退回 |
| `accepted` | 下游确认内容可作为输入 | 开始不依赖固定基线的工作 |
| `baselined` | 下游已将该版本锁定为后续工作的判定依据 | 后续产物引用此版本；变化必须开新版本 |
| `superseded` | 已被新版本替代 | 保留审计，不再作为当前输入 |

【必须】退回时记录退回原因、需要补什么以及退回人；不能直接改写已提交产物后假装未退回。
【必须】从 `baselined` 进入新版本时，旧版本改为 `superseded`，新版本重新经过提交与接受。
【应当】下游在接受前检查字段、来源、哈希和自身所需的业务门禁；通用字段齐全不代表业务内容合格。

## 5. 变更与回退

- 内容变化：创建新 `artifact_version`，保留旧版本及其哈希。
- 需要回到旧版本：重新提交旧内容为一个新交接版本，不删除中间历史。
- 交接后发现问题：按所属业务库定义的缺陷、变更或事故路径处理，本篇不替代这些流程。
- 撤销交接：记录撤销原因与影响范围；已经开始的下游工作必须收到停止或重评信号。

## 6. 反模式

- ❌ 上游生成文件后就宣称“下游已经接手”。
- ❌ 同一份交接件在多处各改一份，最后无法判断哪个是真的。
- ❌ 用最新文件覆盖基线，历史验收却找不到当时的内容。
- ❌ 把通用信封当成所有项目共用的完整 PRD。
- ❌ 在公开规范库或信封里复制真实客户敏感信息。
